# Persistent References and Associations: Documentation Map

This directory records the Phlex design work on persistent references (a persistable identification of a data product or of one element of a collection product) and associations (persistable relationships between such elements, optionally carrying payload data). The work is non-normative: nothing here is part of the design document under `../doc/` until it is promoted there. This file is the entry point. It states the direction the work has taken, the decisions made at each branch point, what was rejected and why, and which of those decisions remain open to team-wide revision.

## 1. Direction in one paragraph

The work started by asking what a reference *is* in Phlex and concluded that it is the triple `⟨cell, product, element?⟩`, not a serialized handle (September 2026, [persistent-references-and-associations.md](persistent-references-and-associations.md)). A comparison with art then asked what a reference *looks like to an algorithm author* and produced three candidate C++ shapes, A/B/C, without choosing ([phlex-art-comparison-report.md](phlex-art-comparison-report.md)). Two explorations of shape C ("the framework resolves references before dispatch; algorithms see only handles") followed: a first pass that described an architecture but did not build it ([2026-09-17](#2026-09-17--first-option-c-exploration)), and a second, independent pass that produced a working prototype in the framework and the staged roadmap now proposed ([2026-10-30](#2026-10-30--second-option-c-exploration-with-prototype)). The current direction is: **Option C, carried by framework-owned `association<L, R, D>` products, with references minted from handles or as framework-bound local tokens, consumer scope declared at registration, and the data-description DSL deferred until (and unless) references are embedded in user product types.**

## 3. Chronology

### 2026-09 — representation analysis

[persistent-references-and-associations.md](persistent-references-and-associations.md). Brief: how to describe references and associations "in the context of an interface/data description language". Findings that have held since:

- The identity of a reference is `⟨cell_coord, product_spec_id, element_index?⟩`; two of the three parts already exist as `data_cell_index` and `product_specification`.
- Associations are intended to be data products (`association<A, B, D>` placeholder in the mock workflow).
- ROOT IDL must remain an output of FORM, never user-authored.
- Protobuf and Cap'n Proto do not express typed references with cardinality, direction, or cell scope; the broader "no IDL suffices" claim was flagged as unproven and a wider survey recommended (done 2026-10-30, Appendix A of the current design).

Its recommendation (Phlex-native description + generator, "Option A" *of that document*, not to be confused with the C++ shape Option A below) is still the fallback if embedded references are ever required; see decision D7.

### 2026-09 — art comparison

[phlex-art-comparison-report.md](phlex-art-comparison-report.md). Brief: [phlex-art-comparison-prompt.md](phlex-art-comparison-prompt.md). Characterised art's `Ptr`/`Assns`/`PtrMaker`/`FindManyP` lifecycle; defined three algorithm-facing C++ shapes:

- **A** value-type `ref<T>` with `resolve(product_store const&)` in algorithm code;
- **B** split `product_ref<T>` / `element_ref<T>`, same resolution model;
- **C** framework resolves declared reference inputs before dispatch; algorithms see handles.

Explicitly left the choice to the team (OD-1) and recorded two Option C weaknesses: no way to *output* references, and no model for *forwarding* them. Both are resolved in the current design (D2, D3).

### 2026-09-17 — first Option C exploration

[persistent-references-explorations-2026-09-17_01-result.md](persistent-references-explorations-2026-09-17_01-result.md) (prompt and transcript alongside; a condensed second pass is `_02-result.md`). Produced with a low-cost model and no build. Proposed: a global `CellRegistry` singleton for cross-cell lookup; `input_association<L,R>(label)` / `output_association` registration keywords with an `.in_cell()` string qualifier; `query::many<T>` views; a `ref_to`/`mint_ref` minting helper; a YAML schema with a code generator producing ROOT dictionaries and a `phlex_ref ⇔ Token` mapper as a first-stage deliverable; service-provider injection; conditional outputs.

Useful contributions carried forward: the `ref_to(handle, index)` minting idea; the lifecycle-wide acceptance framing (persistence round-trip and schema evolution as first-class tests); the list of harder future use cases (dynamic cell creation, per-element payload variation, association-payload evolution, Python algorithms, high-frequency cross-cell lookup), now recorded as D15. Superseded points are itemised in Section 4; the independent comparison ([persistent-references-comparison-2026-10-30.md](persistent-references-comparison-2026-10-30.md)) records which 09-17 proposals were explicitly rejected (the global registry), deferred (schema generation), or carried forward.

### 2026-10-30 — second Option C exploration, with prototype

[persistent-references-explorations-2026-09-30-result.md](persistent-references-explorations-2026-09-30-result.md) (brief: [persistent-references-explorations-2026-09-30-prompt.md](persistent-references-explorations-2026-09-30-prompt.md)). Conducted *de novo* (the 09-17 documents were not read). Produced the design summarised in Section 1 and a validation prototype on framework branch `persistent-references-option-c` (model layer is a candidate implementation; core layer is design validation only, see the design's status note): model types (`reference_token.hpp`, `association.hpp`), core resolver and registration glue, three Catch2 tests including two whole-graph executions, 137/137 ctest passing, 81.7 % line coverage on new files. The design lead resolved four decision points during the work (D3, D4, D5, D8 below). An independent comparison with the 09-17 design ([persistent-references-comparison-2026-10-30.md](persistent-references-comparison-2026-10-30.md)) found one defect (binding did not validate local references; fixed, D13), one overclaim ("covers every requirement"; corrected in the design's summary), and several 09-17 acceptance criteria that had been dropped without comment (now D15).

Subsequent validation found that association `type_id`s were invalid, so the graph did not enforce the association concept as the design claimed (D16). That correction is now implemented and verified on the uncommitted branch: association IDs contain ordered left/right/payload child IDs, and the graph regression rejects a suffix/type mismatch before any algorithm runs. The full suite remains 137/137 because the added Catch2 cases extend existing executables; the 81.7 % coverage figure above predates D16 and has not been remeasured.

## 5. Open questions for team review

The design's own assessment of what is met, partial, deferred, and not claimed is in [§11 of the 10-30 design](persistent-references-explorations-2026-09-30-result.md#11-self-assessment-against-the-brief).

1. D1: is a mandatory `cell_coordinate` acceptable, given it costs a layer path per token? (Mitigation if not: a per-file coordinate table with tokens holding an index, which FORM's navigation tables already resemble.)
2. D5: is three selectors per association input acceptable registration verbosity, or should a Jsonnet helper / `resolve_all<>()` be provided before adoption?
3. D6: for descendant/sibling targets, is a gather port the right primitive, or should the scheduler expose a cell-scoped store lookup to the resolver only (never to algorithms)?
4. D7: does any planned DUNE algorithm *require* embedded references rather than association products? The answer decides whether the DSL is a stage-4 item or never.
5. D11: should the FORM round-trip be prototyped before the design is promoted to `../doc/`, or is the token layout sufficiently determined by the model types? The independent review argues for prototyping: the ROOT TBranch reader requires dictionaries for non-fundamental types, so "one generic layout" is a proposal until demonstrated.
6. D14: is whole-association, both-sided resolution acceptable as the only mode, or does Q9 of the brief require per-side selection before adoption?
7. Promotion: the review recommends documenting three contracts separately when promoting to `../doc/` (algorithm-facing minting/forwarding/lifetime; scheduler-facing scope/readiness/retention; storage-facing identity/round-trip/evolution), each with implemented/proposed/deferred status. Agree on this structure before writing `data_modeling.rst`.

## 6. Terminology

Terms follow `../doc/appendices/glossary.rst`. Within this directory:

- **token** / `element_token`: the persistable identity triple.
- **bound** reference: holds a complete token. **local** reference: names an output of the minting algorithm and is bound by the framework after return.
- **target scope**: the products a consumer's registration declares its tokens may point into.
- **resolved view**: the transient `resolved_association<L,R,D>` handed to an algorithm; never persisted.
- "Option A/B/C" refers to the C++ shapes of the art report unless a document explicitly says otherwise (the 2026-09 analysis used A/B/C for *IDL strategies*).

## 7. D16 correction and validation record (association type identity)

The original inconsistency was between the design's claim of association-type matching during edge making and the prototype's invalid `type_id` for a non-aggregate `association<L,R,D>`. Invalid type IDs bypassed type matching, so a suffix/type mismatch could reach retrieval rather than being rejected while building the graph. The correction below is implemented and verified on `persistent-references-option-c`; no commit reference exists because the work is uncommitted.

1. **Association concept.** [type_id.hpp](../../phlex/phlex/model/type_id.hpp) now sets `0x80` for an association and `0x40` for children (`0xC0` combined), adds `is_association()`, and constructs ordered child IDs for L, R and D (`void` when absent). A forward declaration and an internal trait avoid an include cycle through `association.hpp`. Existing hashing, comparison, formatting and exact RTTI behavior are unchanged, as is the `0xFF` fallback for other unsupported classes.
2. **Model and selector tests.** [type_id_test.cpp](../../phlex/test/type_id_test.cpp) covers validity, flags, ordered child formatting, endpoint and payload differences, comparison, hashing, qualifiers and containers. [reference_resolution_test.cpp](../../phlex/test/reference_resolution_test.cpp) replaces the defect-pinning case with `Type identity of an association product is distinguishable` and verifies positive and negative selector matches. Concept equality remains structural, not exact C++ type equality.
3. **Graph regression.** [resolved_association_test.cpp](../../phlex/test/resolved_association_test.cpp), `Association type mismatch is rejected before graph execution`, registers forward and reverse association outputs with one creator and layer, then deliberately combines one output's suffix with the other's concept. `g.execute()` reports an unmatched required product during graph finalization, with zero provider, producer and consumer invocations.
4. **Verification.** The full container build succeeds and CTest reports `100% tests passed out of 137`. The new Catch2 cases extend existing test executables, so no extra CTest entry was needed. Scoped `prek` passes for the four changed files; an isolated two-translation-unit probe also passes identity, exact RTTI, hashing and formatting checks. The last coverage measurement is the pre-D16 81.7 % baseline, not a measurement of the corrected branch.

This closes D16's implementation inconsistency, not the wider questions of persistence, selective resolution, type-concept policy or readiness for adoption. The general unsupported-class fallback remains a pre-existing framework limitation and was deliberately outside this correction.

## 8. Next design and prototyping gates

These gates describe recommended work, not authorization to implement, commit, push or promote the design. The model layer remains a candidate implementation and the core layer remains a validation prototype; completing D16 does not change that classification.

1. **Agree the runtime contract and target use cases.** Review D1 (logical identity), D5 (declared targets), D14 (whether Q9 needs per-side or filtered resolution), and borrowed-view lifetime. Write out a representative five-association consumer and decide which requirements must be met in the next prototype. Acceptance: recorded decisions distinguish full-association selection from endpoint/row selection, specify that views do not own target products, and preserve all deferred requirements in the ledger.
2. **Complete the focused runtime evidence.** Add a producer → forwarding transform → consumer graph, a transform with resolved inputs, and a predicate with resolved inputs. Test identity preservation, data/payload access, failure before affected user-code invocation, and the same-cell/ancestor-cell cases. Remeasure coverage including the D16 changes and run the full suite and scoped hooks. Acceptance: the runtime contracts are demonstrated beyond the currently tested observer path; this need not add fold/unfold support unless required by gate 1.
3. **Run the Stage 1 FORM persistence spike before promotion.** Start with a bounded association product, with and without payload, and exercise write → separate-process read → pre-dispatch resolution through the existing ROOT TTree and RNTuple backends. Check logical token identity, values, payloads, cell/stage identity and invalid-target failures; establish what dictionaries or backend adapters are actually required rather than assuming one generic layout is sufficient. Include a small old-schema/payload-evolution fixture or explicitly identify the missing migration contract. Acceptance: reproducible round-trip tests plus a documented persistence layout and remaining backend limitations. This is the next substantial feasibility experiment; it does not require committing to a custom DSL first.
4. **Choose the candidate core implementation from evidence.** Once gates 1–3 bound the required behavior, measure resolution time and memory on representative high-multiplicity associations. Compare the current row vector plus hash maps with alternatives only where measurements justify them; settle registration diagnostics and compile-time arity checking. Acceptance: a reviewed runtime API and representation with measured tradeoffs, rather than treating the validation code as production-ready.
5. **Design broader cross-cell scheduling separately.** If descendant/sibling targets are required, specify gather or resolver-only lookup semantics, completion/readiness, ownership and retention, eviction, and dynamic-cell behavior before implementing Stage 2. Include multiple producers/stores per cell and nested cells with repeated local numbers. Acceptance: an explicit scheduler contract and tests, not merely a global lookup map.
6. **Promote only the agreed contracts.** After the preceding review and feasibility gates, decide whether embedded reference members require generated traversal/views and whether a custom DSL is justified compared with traits or handwritten adapters. Separate algorithm-facing, scheduler-facing and storage-facing contracts when promoting agreed material into `../doc/`. A model-only PR can be considered earlier after team review, but would remain explicitly limited in scope; creating commits or PRs requires a separate request.
