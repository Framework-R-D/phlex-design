## Questions

1. We are uneasy about the current draft design inasmuch as it allows erroneous hand-fabricated tokens to be stored in an association, and not discovered until those data are read, possibly months later. Is there a way to enable verification before the FORM backend writes the data?
2. Associations appear to be restricted currently to one cell coordinate per side; doesn't this mean that not every reference pair should need to carry both cell coordinates along with them?
3. Is it possible for an algorithm to interrogate product metadata for a target (as opposed to the optional "D" association pair-specific user product)? If so, what framework-specific information would need to be provided to the algorithm, and how?
4. If we need to revisit D3, can we store enough metadata with the association (see technical design) to allow multiple targets per side without requiring consumer resolution to specify a port for every target or provide explicitly all targets to `resolve<>` (unless filtering by target is required by the algorithm), or requiring a global store? Based on Art's Association's capabilities, and the use thereof by experiments, this is likely to be a DUNE requirement, even if not currently specified as such.
5. According to the survey (appendix), EDM4HEP and Key4hep / k4FWCore both make use of PODIO despite themselves being licensed via Apache 2.0. Either both projects are in legal jeopardy, or they have found a way to use PODIO without infringing its GPL 3.0 license. Please examine these projects and their public-facing authoritative information to ascertain which of these is more likely to be the case; if the latter, we may be able to use PODIO ourselves without a clean-room reimplementation.
